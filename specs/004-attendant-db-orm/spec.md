# Feature Specification: Attendant Database Persistence and ORM Governance

**Feature Branch**: `004-attendant-db-orm`

**Created**: 2026-05-29

**Status**: Draft

**Input**: User description: "Remove the attendant mock data and let attendants be created normally in the database. Create an ADR making ORM usage mandatory for database manipulation, and require migrations to always be generated by terminal commands so database changes remain coherent."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start With Real Attendant Data (Priority: P1)

An administrator opens the delivery attendants page in a fresh workspace and sees the
real persisted attendant list, not preloaded sample attendants.

**Why this priority**: The attendant list is operational data. Showing mock attendants
as real employees can lead operators to transfer sessions to people who do not exist.

**Independent Test**: A tester can open the application with a clean local workspace,
go to the attendants page, confirm that no sample attendants appear, add one real
attendant, restart the application, and confirm that the same attendant remains saved.

**Acceptance Scenarios**:

1. **Given** a clean workspace with no saved attendants, **When** the administrator
   opens the delivery attendants page, **Then** the page shows the empty state and no
   mock employees.
2. **Given** the attendants page is empty, **When** the administrator creates a valid
   attendant, **Then** the attendant is saved as real operational data and appears in
   the list.
3. **Given** an attendant was saved, **When** the application is reopened, **Then** the
   saved attendant still appears with the same identity, WhatsApp, photo, and status.

---

### User Story 2 - Prevent Mock Data From Affecting Operations (Priority: P2)

An operator transfers delivery sessions only to attendants that were actually saved in
the local workspace.

**Why this priority**: Transfer eligibility must be based on accountable employees,
not test fixtures or fallback records.

**Independent Test**: A tester can open a clean workspace, confirm that no transfer
target is available before creating an attendant, create and mark an attendant online,
and confirm that only that saved attendant can be selected.

**Acceptance Scenarios**:

1. **Given** no attendants are saved, **When** a session transfer is started, **Then**
   the system explains that no online attendant is available instead of showing sample
   names.
2. **Given** one saved attendant is online, **When** a session transfer is started,
   **Then** that saved attendant is available as the transfer target.
3. **Given** test data exists only for automated tests or documentation, **When** the
   production workspace is used, **Then** that data never appears in operational lists
   or transfer controls.

---

### User Story 3 - Record Database Governance Rules (Priority: P3)

A maintainer has a documented architecture decision that defines how database records
are manipulated and how schema changes are produced.

**Why this priority**: Consistent data access and repeatable schema changes reduce
drift between code, migrations, and the local database.

**Independent Test**: A reviewer can locate the architecture decision, verify that it
requires the approved database access pattern for application data, and verify that
schema changes include the command used to generate their migration.

**Acceptance Scenarios**:

1. **Given** a maintainer reviews database-related work, **When** they open the
   architecture decision, **Then** it states that database manipulation must use the
   approved ORM-based access path.
2. **Given** a schema change is proposed, **When** the change is reviewed, **Then** the
   generated migration is accompanied by the terminal command used to create it.
3. **Given** a database change bypasses the documented access path or handwrites a
   migration without an accepted exception, **When** it is reviewed, **Then** the
   change is considered non-compliant.

### Edge Cases

- A clean workspace must not silently seed attendants during startup or navigation.
- If the database cannot be loaded, the attendants page must show an actionable error
  rather than falling back to mock records.
- Automated tests may use fixtures, but fixtures must remain isolated from production
  runtime data.
- Existing saved attendants must remain available after mock records are removed.
- Migrations must not create sample attendants unless a future explicit demo/import
  mode is approved.
- If a generated migration requires manual review, the review must preserve the
  generated command traceability.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST remove mock attendants from the runtime source used by the
  delivery attendants page.
- **FR-002**: System MUST show an empty attendant state when no attendants have been
  saved in the local workspace.
- **FR-003**: System MUST allow an administrator to create a first real attendant from
  the attendants page without relying on seeded data.
- **FR-004**: System MUST persist created attendants so they remain available after
  application restart.
- **FR-005**: System MUST preserve the saved attendant attributes required by delivery
  operations, including name, display name, WhatsApp, photo, and online/offline status.
- **FR-006**: System MUST base session transfer targets only on saved active attendants
  that are eligible for transfer.
- **FR-007**: System MUST NOT display test fixtures, documentation examples, or fallback
  mock attendants in operational attendant lists or transfer controls.
- **FR-008**: System MUST show a clear error when attendant data cannot be loaded from
  the local workspace.
- **FR-009**: System MUST provide an architecture decision record defining the required
  database manipulation policy for application-owned data.
- **FR-010**: The architecture decision record MUST require ORM-based database access
  for application-owned database reads and writes unless an explicit exception is
  recorded.
- **FR-011**: The architecture decision record MUST require schema migrations to be
  generated through terminal commands and reviewed with the command trace retained.
- **FR-012**: Future database-related changes MUST be reviewable against the
  architecture decision record before they are accepted.

### Key Entities

- **Delivery Attendant**: A human delivery employee saved by an administrator and used
  as a real operational transfer target.
- **Operational Attendant List**: The persisted set of attendants shown to operators
  and administrators in the delivery workflow.
- **Architecture Decision Record**: A durable decision document describing the
  required database access and migration generation rules for maintainers.
- **Migration Trace**: The recorded command and review context that proves a schema
  migration was generated through the approved workflow.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In a clean workspace, 0 mock attendants appear in the attendants list or
  transfer target controls.
- **SC-002**: An administrator can create the first real attendant from the empty state
  in under 2 minutes.
- **SC-003**: 100% of saved attendants remain visible after application restart with
  their required operational attributes intact.
- **SC-004**: 100% of transfer target options come from saved active attendants and do
  not include mock-only data.
- **SC-005**: A reviewer can locate the database governance decision in under 30
  seconds from the repository root.
- **SC-006**: 100% of future schema changes can be traced to a recorded generation
  command or an explicitly documented exception.

## Assumptions

- This feature updates the currently implemented delivery attendants workflow rather
  than adding a separate employee module.
- Test fixtures may continue to exist inside automated tests when they are not loaded
  by production runtime paths.
- Existing real attendant records should be kept; only runtime mock or seeded
  attendants should be removed from operational behavior.
- The architecture decision applies to application-owned database records and schema
  changes going forward.
- Tool choice and migration command details will be finalized during planning, but the
  requirement for an ORM-based access path and command-generated migrations is fixed.
