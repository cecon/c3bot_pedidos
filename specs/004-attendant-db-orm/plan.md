# Implementation Plan: Attendant Database Persistence and ORM Governance

**Branch**: `004-attendant-db-orm` | **Date**: 2026-05-29 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-attendant-db-orm/spec.md`

## Summary

Remove runtime attendant seed data from the delivery attendants workflow, load
attendants only from the local SQLite workspace database, and make the empty state the
default for a clean workspace. Introduce a typed ORM access boundary for
application-owned database reads/writes, document the migration command workflow in an
ADR, and require future schema changes to be generated from terminal commands instead
of handwritten SQL.

## Technical Context

**Language/Version**: TypeScript 5.8, React 19, Rust 2021 edition

**Primary Dependencies**: Existing Tauri 2, Vite 7, Mantine 9, Mantine form/hooks,
Lucide React, Tauri SQL plugin, Vitest 4, Testing Library, and StrykerJS 9. Add
Drizzle ORM for typed SQLite access and Drizzle Kit for schema/migration command
generation. Keep existing UI and desktop dependencies.

**Storage**: SQLite local database (`sqlite:c3bot.db`) remains the only application
database. Drizzle schema definitions become the typed source for application-owned
tables. Existing Tauri migrations remain historical migrations; future schema
migrations are generated by Drizzle Kit and then registered with the Tauri SQL plugin
migration list.

**Testing**: Vitest unit tests for the ORM mapping, attendant persistence load states,
empty-state behavior, and transfer eligibility with no seeded attendants; component
tests for the attendants page; StrykerJS mutation coverage for shared attendant and
persistence decision rules; TypeScript typecheck, Vite build, and Cargo check.

**Target Platform**: Windows desktop first through Tauri. Vite browser validation
remains available, but database-backed attendant operations are available only in the
Tauri runtime and must not fall back to mock attendants.

**Project Type**: Local-first desktop admin application.

**Performance Goals**: Loading attendants from the local database should complete in
under 1 second for hundreds of attendants. Creating, updating, deleting, or changing
status should provide visible feedback in under 1 second. Transfer controls should
reflect the persisted online/offline list without adding noticeable navigation delay.

**Constraints**: Dark operator UI; no landing page; no runtime attendant seed data;
no fallback from database failure to mock attendants; WhatsApp and Base64 photo data
must not be logged; direct SQL is limited to the ORM proxy/adapter and migration
registration boundary; schema changes must retain a generated command trace.

**Scale/Scope**: One persistence refactor for delivery attendants, one ORM schema and
adapter boundary, package scripts/configuration for migration generation, one ADR
already created for governance, focused tests, and plan/task documentation. No new
database engine, UI framework, or external service integration.

**Structure Decision**: Keep the existing single Tauri/Vite application. Add a small
`src/db/` boundary for Drizzle schema, client construction, and the Tauri SQL proxy
adapter. Keep attendant business rules in `src/domain/attendants.ts`, keep the UI in

and any migration that must run in the Tauri plugin is registered from that generated

## Phase 0 Research Summary

The implementation will use Drizzle ORM because it supports typed SQLite schemas and
queries while allowing a custom proxy driver that can call the existing Tauri SQL
plugin. Drizzle Kit is selected for command-generated migration files. The Tauri SQL
plugin remains responsible for opening the local SQLite database and applying
registered migrations. Mock attendants are removed from runtime application inputs;
tests may keep explicit fixtures. Browser-only Vite runtime must not fabricate
attendants when SQLite is unavailable.

## Phase 1 Design Summary

The data model adds an explicit persistence load state, an ORM attendant row model,
and migration governance records around the existing delivery attendant entity. The
attendant persistence contract defines clean workspace empty state, create/restart
persistence, database error behavior, and transfer target sourcing. The governance
contract defines the ORM-only access rule, generated migration command trace, review
rules, and allowed exceptions.
