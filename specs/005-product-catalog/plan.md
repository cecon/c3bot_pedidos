# Implementation Plan: Product Catalog (iFood-aligned, destination-mapped)

**Branch**: `005-product-catalog` | **Date**: 2026-06-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/005-product-catalog/spec.md`

## Summary

Build a local-first product catalog whose **data model mirrors the iFood Food catalog
structure** (store → catalog → category → product/item → option groups → options, plus
pizza and combo templates), so that a future destination integration can map every
sellable element through reserved external-reference fields without redesigning the
schema. Scope is the **data model + operator maintenance UI only**: no synchronization is
built now, the product is single-store/single-tenant, and the pizza pricing strategy is a
configurable, extensible setting. Implementation evolves the existing oversimplified
`products` table into the full hierarchy using a Drizzle-generated migration, adds pure
domain rules (price validation, alphanumeric CNPJ validation, option-group rules,
availability resolution across store/catalog/category/item scope, pizza pricing, mapping
readiness) with unit + mutation tests, and surfaces it — including a store-profile editor
and multi-catalog management with per-weekday hours — in the existing dark `CatalogPanel`
workspace. The catalog reads/writes through HTTP endpoints on the existing local C3Bot API
(the same `node:http` server as attendants); **all** endpoints (existing + catalog) are
described by a single **OpenAPI/Swagger** document, with an interactive Swagger UI reachable
from a new **"API / Docs"** workspace menu entry.

## Technical Context

**Language/Version**: TypeScript 5.8, React 19, Rust 2021 edition.

**Primary Dependencies**: Tauri 2, Vite 7, Mantine 9 (+ form/hooks), Lucide React, Tauri
SQL plugin, Drizzle ORM + Drizzle Kit (typed SQLite access and generated migrations),
Vitest 4 + Testing Library, StrykerJS 9. The local C3Bot API is the existing
`node:http` server (`scripts/attendant-api.ts`, no web framework); this feature extends it
with catalog routes and adds **`swagger-ui-dist`** (bundled offline Swagger UI assets) to
serve interactive docs. No web framework (Express/Fastify) is introduced.

**Storage**: SQLite local database (`sqlite:c3bot.db`). Drizzle schema in
`src/db/schema.ts` is the typed source of truth; migrations are generated by Drizzle Kit
and registered with the Tauri SQL plugin migration list in `src-tauri/src/lib.rs`
(next file: `003_product_catalog.sql`). Prices stored as integer cents (BRL).

**Testing**: Vitest unit tests for catalog domain rules and persistence state; component
tests for the catalog UI; StrykerJS mutation coverage (≥85% break threshold) on the shared
pricing/availability/validation/readiness rules; `pnpm typecheck`, `pnpm test`,
`pnpm test:mutation`, `pnpm build`, and `cargo check`.

**Target Platform**: Windows desktop first via Tauri; Vite browser validation available,
but database-backed catalog operations run in the Tauri runtime (no mock fallback for
persisted data).

**Project Type**: Local-first desktop admin application (single project; `src/` frontend +
`src-tauri/` Rust shell + a local `node:http` API in `scripts/` consumed via
`VITE_C3BOT_API_BASE_URL`). The catalog frontend reads/writes through HTTP endpoints on this
API, exactly like the attendant feature.

**Performance Goals**: Browse/search a catalog of ≥200 products and add to an order in
under 10 seconds of operator interaction (SC-002); create a basic catalog (1 catalog, 3
categories, 10 products) in under 15 minutes (SC-001); catalog reads complete in under 1
second for hundreds of items; paused-item auto-return reflected within one minute (SC-006).

**Constraints**: Dark operator UI, no landing page; single store per installation (no
tenant selection); no synchronization/integration code in this feature (external-reference
fields only); direct SQL limited to the ORM proxy/adapter and migration registration;
schema changes generated via Drizzle Kit command trace; no PII/secrets logged.

**Scale/Scope**: One store, multiple catalogs/categories, hundreds of products, option
groups, and pizza/combo templates. New schema (≈15 tables), one generated migration, one
domain rules module + persistence module, catalog UI expansion, ~30 HTTP endpoints on the
existing local API with an OpenAPI doc + Swagger UI, and one new menu entry. No new database
engine, UI framework, or external service (only `swagger-ui-dist` for offline API docs).
